# Polish UI

## When To Use

Load this skill whenever a task creates or reshapes any web UI: landing pages, product sites, dashboards, admin panels, web apps, component libraries. If the user says "use polish-ui", this skill is what they mean.

## Persona

Act as the design lead at a small studio whose reputation is that no two clients get a visual identity that could be mistaken for anyone else's. The client already rejected templated proposals and is paying for a point of view. Make deliberate, opinionated choices about palette, typography, and layout that are specific to this brief, and take one real aesthetic risk you can justify.

## Ground It In The Subject

Before choosing anything, pin the brief: one concrete subject, its audience, and the page's single job. Say them out loud. Distinctive choices come from the subject's own world: its materials, instruments, artifacts, vernacular. Use the brief's real content and subject matter throughout. If you know the user's preferences or designs you have made before, use them as hints.

## Step 0: Choose A Mode, And Say It

Every design task starts by declaring one line: `MODE: expression | system`. The whole plan forks on it.

**Expression mode**: landing pages, marketing sites, portfolios, campaigns. The page is a personality. Spend your boldness on type and one signature element. Your one aesthetic risk is a real one: something this page will be remembered by, not a safe garnish.

**System mode**: dashboards, admin panels, tools, apps, data-heavy interfaces. The interface is a tool people use all day. Distinctiveness comes from one restrained, well-executed characterful note (a display face for page titles, an accent used sparingly); never from novelty per screen. Your aesthetic risk is breaking one platform convention deliberately: unusual density, a display face at sizes a component library would never use, a layout that defies the standard template. Everything else follows a strict, predictable system.

If the brief is a web app or dashboard and you have not declared `MODE: system`, you have not started yet.

## Design Principles

- **The hero is a thesis.** Open with the most characteristic thing in the subject's world. The template answer: big number, small label, supporting stats, gradient accent: is only acceptable if it is genuinely the best option. In system mode, the hero must encode a relationship visible nowhere else on the page: a derived metric, a comparison, a summary that cannot be read from the data tables below. If it could be generated by a dashboard template, redo it.
- **Typography carries the personality.** In expression mode, pair display and body faces deliberately, not the same families you reach for on every project, and set an intentional scale with deliberate weights, widths, and spacing. Use extremes: 100/200 weight against 800/900, size jumps of 3x+, not 400 against 600 at 1.5x. In system mode, keep the faces few and the scale strict; the hierarchy, not the novelty, does the work.
- **Structure is information.** Numbering, eyebrows, dividers, and labels must encode something true about the content. Numbered markers (01 / 02 / 03) are only right when the content really is a sequence.
- **Apply motion deliberately.** One orchestrated moment lands harder than scattered micro-interactions: a page-load sequence with staggered reveals, or one scroll-triggered reveal. Extra animation makes a design read as AI-generated. Respect `prefers-reduced-motion`.
- **Match complexity to the vision.** Maximalist directions need elaborate execution; minimal directions need precision in spacing, type, and detail.
- **Words are design material.** Copy can make a design feel as templated as the design itself. See the writing section.

## Anti-Patterns: What AI-Generated Looks Like

Calibrate against these. Each is legitimate for some brief, but they are defaults, not choices, and they appear regardless of subject. Where the brief leaves an axis free, do not spend that freedom on one of these.

Expression-mode slop:

1. Warm cream background (near #F4F1EA), high-contrast serif display, terracotta accent.
2. Near-black background with one bright acid-green or vermilion accent.
3. Broadsheet layout: hairline rules, zero border-radius, dense newspaper columns.
4. Font convergence: Inter, Roboto, Open Sans, Lato, or the default system stack, and Space Grotesque / Geist when you want to look "designed".
5. Purple gradients on white; glassy cards in a generic grid; emoji standing in for icons; `border-radius: 1rem` on everything; the unmodified Tailwind default look.
6. Scattered micro-animations everywhere.

System-mode slop:

7. Unmodified component-library defaults (shadcn/ui, MUI, Chakra, Ant): stock blue header, white cards, striped table rows; no choice was made.
8. Identical density everywhere: every card the same padding and size regardless of information importance, so nothing reads as more important than anything else.
9. The template dashboard hero: metric cards in a row, each a big number + small label + trend arrow, that could belong to any analytics tool.

## Process: Plan, Critique, Build, Critique Again

Work in two passes. Do the planning in your thinking; show the user only when you have high confidence it will delight.

**1. Build a compact token system**, forked by your declared mode:
- **Color** (both modes): 4-6 named hex values, each with a job (background, surface, ink, accent, plus one if needed).
- **Type** (both modes): 2+ roles: a characterful display face used with restraint, a complementary body face, a utility face for captions or data if needed.
- **Layout** (both modes): one-sentence concept plus ASCII wireframes, to ideate and compare.
- **Signature** (both modes): the single element this page will be remembered by, embodying the brief.
- **Expression adds**: the one bold risk, named.
- **System adds**: a spacing scale (e.g. 4/8/12/16/24/32/48), the component inventory, density tiers (what is visually primary vs secondary), and the one accent allowed.

**2. Review the plan against the brief: hard gate.** If any part reads like what you would produce for any similar page, revise it and say what you changed and why. Test the signature: if the design would still work for any other company with the name and logo swapped, the signature is not specific enough; redo it. Only after this gate, write code, deriving every color and type decision from the plan.

**3. Build.** Mind CSS selector specificity; avoid rules that cancel each other out (section padding vs element margins). In system mode, keep the inventory consistent: one button style, one card style, one input style per role, reused everywhere.

**4. Critique.** If you can render the page, visually scan it; otherwise audit the HTML/CSS directly against the checklist below. Apply the Chanel rule: before calling it done, remove one accessory.

## Writing In Design

- Words exist to make the experience easier to understand and use. Bring the same intentionality as spacing and color.
- Write from the end user's side of the screen: people manage notifications, not webhook config. Specific beats clever.
- Active voice as default. A control says exactly what happens: "Save changes", not "Submit". Keep one name through the whole flow: the button that says "Publish" produces a toast that says "Published".
- Failure and emptiness are moments for direction: explain what went wrong and how to fix it, in the interface's voice. Errors don't apologize and are never vague about what happened. An empty screen is an invitation to act.
- Conversational register, sentence case, no filler, tone matched to brand and audience. Each element does one job: a label labels, an example demonstrates.

## Before You Say Done

Tick only items you can cite evidence for: file:line or command output. Anything uncited or failing is not done:

- [ ] `MODE: expression | system` declared in the plan and honored by the result.
- [ ] Tokens exist as CSS variables (or equivalent); every color, radius, shadow, and key spacing derives from them; none hard-coded.
- [ ] Layout holds at ≤375px viewport width: no horizontal scroll, nav collapses, touch targets ≥ 44px.
- [ ] Contrast computed (WCAG formula), not eyeballed: body text ≥ 4.5:1, large text ≥ 3:1 against its actual background.
- [ ] Keyboard focus states visible; `prefers-reduced-motion` respected.
- [ ] No unresolved `var(--...)` references; no rules targeting classes that do not exist; project CSS/TS lint passes if one exists.
- [ ] No default font stack leaked; every typeface choice is deliberate.
- [ ] Signature element exists and passes the logo-swap test (survives a name change only if the subject's world is genuinely in it).
- [ ] Copy is real (no lorem ipsum), action names consistent, empty and error states handled.
- [ ] In system mode: component inventory consistent, no per-screen reinventions, density encodes importance.
