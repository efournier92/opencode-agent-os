## Context & Motivation

The user's highest-value workflow is the critical eye: specify, build, attack, rebuild, attack again, accept the reviews. That pattern is currently improvised per session, its findings live only in transient chat, and its vantage points are limited to four lane-locked critics (`claim-critic`, `product-critic`, `compliance-officer`, `visual-critic`). Nothing covers security, scale, reliability, cost, abuse, or data integrity, and nothing carries findings between agents or across rounds.

This spec institutionalizes that workflow as one operator-run loop, `grill`. It fans out diverse adversarial lenses, records every finding in a shared committed ledger, lets agents rebut and un-ship each other's work, converges on evidence, then puts only the genuinely human-only decisions to the user interactively, batched and capped, before offering to ship.

Two decisions were resolved by dispatch during design and shape this spec:

- **Nesting stays flat.** An external evidence pass and an adversarial internal attack both recommended against enabling subagent nesting. The external pass found multi-agent token multipliers around 15x, diminishing returns past a capability-saturation point, and no evidence that a reviewer spawning an implementer helps (`https://www.anthropic.com/engineering/multi-agent-research-system`, `https://arxiv.org/abs/2512.08296`, `https://arxiv.org/abs/2503.13657`). The attack found that `models.yaml:30-34` forbids granting a subagent `task`, that zero triggers have fired (`models.yaml:29`), and that raising depth is a managed-key change with installer blast radius. So "a critic spawns builders" is realized as **the operator routes critic findings to builders**, and the loop ships at depth 2.
- **Markdown ledger first.** The storage pass recommended a committed Markdown ledger with operator-serialized writes, graduating to SQLite only on a documented trigger (`https://www.sqlite.org/whentouse.html`, `https://jsonlines.org/`).

Source discovery entries: `D-20261004-10` (deferred reduce/synthesis rule, now triggered by wide fan-out), `D-20261004-02` (loop-readiness triage), `D-20261005-08` and `D-20261005-11` (critic seats run at max effort).

## Glossary

Links `docs/GLOSSARY.md`; every definition the requirements depend on is inlined so this spec stands alone.

**Adversary**: a read-only critic dispatched with one assigned attack lens against a candidate solution; returns evidence-backed findings, never fixes. _Avoid_: red-teamer, devil's advocate, reviewer. Defined here.

**Adjudicator**: the read-only convergence gate that classifies ledger findings as settled-by-evidence or human-only and emits the minimal walkthrough agenda. _Avoid_: synthesizer, summarizer, judge. Defined here.

**Critique ledger**: the committed per-run record of findings, with IDs, severities, statuses, and rebuttals, that is the loop's shared state. _Avoid_: findings doc, notes, log. Defined here.

**Round**: one full diverge-attack-rebut cycle of the loop. _Avoid_: iteration, pass, cycle. Defined here.

**Walkthrough**: the interactive final stage where the operator puts only human-only decisions to the user through the `question` tool. _Avoid_: review, sign-off, approval. Defined here.

**Convergence**: the state where a round adds no new high-severity finding and every high or medium finding is settled with evidence. _Avoid_: done, finished. Defined here.

**Quality gate** and the discovery terms keep their existing meanings (`docs/GLOSSARY.md`).

## Goals

- One repeatable, operator-run loop that turns a goal into a sound, evidence-converged, safe-to-ship solution.
- Vantage diversity: attack from many independent lenses, not one critic's opinion.
- A shared committed ledger so findings and rebuttals survive across agents and rounds.
- Agents criticize each other and delete unearned work, not just add.
- Convergence decided by evidence and an independent gate, not by the plan's author.
- The user stays in the loop through a curated, capped, batched walkthrough, never a flood.
- Reuse `create-spec`, `implement-spec`, `builder`, `verifier`, `ship-changes`, and the discovery store. Smallest diff.

## User Stories

1. As the user, I want to say "grill this goal" and have the system fan out many critics, so that I get recommendations stronger than my own single view.
2. As the user, I want to answer the design decisions I can up front, so that the loop only researches what I genuinely cannot decide.
3. As the user, I want to say "I don't know" on a decision and have the loop research, analyze, and conclude for me, so that my uncertainty does not stall progress.
4. As the user, I want every finding recorded with evidence in one place, so that I can audit how a conclusion was reached.
5. As the user, I want critics to rebut each other and be settled by executed evidence, so that consensus is not a popularity vote.
6. As the user, I want a dedicated pass that removes unnecessary work, so that the solution does not accumulate speculative scope.
7. As the user, I want an independent adjudicator to decide convergence, so that the agent that built the plan is not the one that blesses it.
8. As the user, I want only the genuinely human-only decisions put to me at the end, so that I am not buried in questions I cannot answer well.
9. As the user, I want those decisions batched and capped with a recommendation each, so that I can accept or override quickly.
10. As the user, I want to add my own criticism during the walkthrough and spawn more rounds, so that my judgment still shapes the outcome.
11. As the user, I want shipping offered only after I explicitly agree with everything, so that nothing ships unapproved.
12. As the operator, I want a skill that orchestrates the existing pipeline, so that I do not duplicate spec and build logic.
13. As the operator, I want the ledger written only by me, so that concurrent writers never corrupt it.
14. As the operator, I want a validator in the repo check, so that ledger format cannot drift.
15. As a future agent, I want convergence decisions indexed in the discovery store, so that later work inherits them.

## Design Principles

- **Operator writes, subagents propose.** Only the operator appends to the ledger; subagents return candidates, matching the discovery write contract.
- **Evidence over vote.** A finding contradiction is settled by an executed `verifier` command or a resolving `path:line` or URL, never by counting opinions.
- **Independent gates.** The adversary and adjudicator run on a different vendor from the DeepSeek operator and builder in the `ds+glm` profile.
- **Minimize the human surface.** The adjudicator shrinks the decision set to true human-only calls before anything reaches the user.
- **Smallest diff.** No new always-loaded prose, no config depth change, no new dependency.
- **Ledger graduation trigger.** Move from the Markdown ledger to SQLite when any one holds: two independent processes must append concurrently; the ledger exceeds roughly 5,000 findings or 2 MB; a run needs more than 3 aggregate or cross-reference queries; or status and rebuttal edits cause recurring merge conflicts. Until then Markdown is the source of truth.

### Schema: The Critique Ledger

Path: `docs/critique/YYYY-MM-DD_Topic.md`, one file per run, created when missing. `docs/critique/` is committed.

Format, exactly:

```markdown
# Critique Ledger: <Topic>

- Goal: <one line>
- Started: YYYY-MM-DD
- Branch: <branch or none>

## Findings

- C-YYYYMMDD-NN | YYYY-MM-DD | <lens> | <severity> | <confidence> | <status> | <finding> | <evidence>
  - rebuttal | <status> | <evidence> | <text>
```

Field rules:

- Finding lines start with `- ` and pipe-separate eight fields: `id | date | lens | severity | confidence | status | finding | evidence`.
- `id` is `C-YYYYMMDD-NN`, and its date part equals the `date` field.
- `lens` is one lowercase token from `security`, `scale`, `reliability`, `cost`, `abuse`, `data-integrity`, `maintainability`, `correctness`, `product`, `compliance`, `visual`, `research`.
- `severity` and `confidence` are each one of `high`, `medium`, `low`.
- `status` is one of `open`, `addressed`, `rejected`, `escalated`.
- `evidence` is a `path:line`, a backticked command, or a URL, and is required for every finding.
- No `|` appears inside any field. A finding line is at most 240 characters. A ledger file is at most 16 KB.
- Rebuttal lines are indented two spaces, start with `rebuttal | `, and never count as findings.

### Resolution Logic: The Loop

The `grill` skill owns the loop. Phases in order:

0. **Intake.** Restate the goal in one line. Run one material question round through the `question` tool (same shape as `skills/create-spec/SKILL.md` Phase 2): 2-4 options per decision, recommended first, no artificial cap, free-text answer kept. Every decision the user cannot answer becomes a `research` finding with status `open` in the ledger. When the goal needs a design document, delegate design to `create-spec`.
1. **Ledger init.** Write the ledger file with the header. The operator is the only writer.
2. **Diverge.** Dispatch in one parallel batch: up to 3 recon agents (`code-locator`, `external-researcher`) to kill `research` findings; N `adversary` dispatches, each a distinct lens; the specialist critics that fit the artifact (`claim-critic`, `product-critic`, `compliance-officer`, `visual-critic`); and `builder` tasks for candidate fixes. Cap tool calls per recon dispatch (for example about 20). Each dispatch follows the Delegation Contract: scope, goal, exact paths, output shape, what not to re-report, shell discipline, `NEED-INPUT` clause. Append returned findings to the ledger with new IDs and status `open`.
3. **Rebut.** Re-dispatch `adversary`, `builder`, and `verifier` to attack the current findings and each other's findings. A contradiction between findings is settled only by a `verifier` command or a resolving evidence pointer. Record each outcome as a `rebuttal | ` line and set the parent finding's status to `addressed`, `rejected`, or `escalated`.
4. **Un-ship.** Dispatch one `adversary` with the `maintainability` lens whose only job is deletion: name the parts of the current solution that are speculative, unearned, or removable, and record them as findings. Removable items are removed, not documented.
5. **Adjudicate.** Dispatch the `adjudicator` with the ledger path and the goal. It classifies every finding as `SETTLED` or `HUMAN`, returns a convergence verdict, and emits the walkthrough agenda.
6. **Walkthrough.** See the Walkthrough requirement.
7. **Ship gate.** Only after the user agrees with everything, offer `ship-changes` through the `question` tool. Never run it unprompted.
8. **Hand Off.** Append `[decision]`, `[question]`, and `[outcome]` entries to `docs/discovery/DISCOVERY.md` by ID; link them from the handoff. Subagents only ever return candidates.

Convergence predicate (checked by the `adjudicator`):

- `CONVERGED` when the latest round added no new `high` severity finding, and every `high` or `medium` finding is `addressed` or `rejected` with evidence, and no `research` finding is `open`.
- Otherwise `NOT-CONVERGED`, naming the blocking findings.
- The loop runs at most 3 rounds. On the cap, the adjudicator escalates every unresolved `high` or `medium` finding to `HUMAN` with status `escalated`.

### Walkthrough

The operator presents the adjudicator's `HUMAN` agenda to the user through the `question` tool, batched, one `question` entry per decision, capped at 7 entries. Each entry states the decision, the recommendation, the strongest counter-argument, and the evidence pointer. Each entry offers `Accept recommendation` (first), `Override`, and `Dig deeper`. A `Dig deeper` answer spawns a mini round on that decision (Phases 2 to 5) before the walkthrough resumes. `SETTLED` findings are listed to the user in one collapsed line as "settled, veto on request"; a veto reopens the item. The loop ends when the user explicitly agrees with everything, which is the only trigger for the ship gate. When the human-only set exceeds 7, the adjudicator folds the lowest-ranked items into trusted defaults that the user can veto, and says so; it never silently drops a `high` severity item.

### Audit Trail

The ledger is the audit trail, committed and git-diffable. The adjudicator's verdict and the final walkthrough agreement are recorded in the ledger's closing lines and indexed in the discovery store.

### Concurrency And Locking

The operator is the sole ledger writer, so no lock is needed. Subagents never write the ledger. This keeps the SQLite graduation trigger dormant by design.

## Production Risks & Mitigations

- **Quota burn from wide fan-out.** Mitigated by per-dispatch tool caps, batched parallel calls, stop-on-answer, and the 3-round cap.
- **Runaway loop.** Mitigated by the evidence-gated convergence predicate and the round cap with escalation.
- **User overload.** Mitigated by adjudicator minimization, the batch cap of 7, acceptance-by-default, and trusted defaults for the overflow.
- **Same-vendor monoculture.** Mitigated by pinning `adversary` and `adjudicator` to GLM lanes in `ds+glm`.
- **Ledger format drift.** Mitigated by `scripts/check_critique.py` inside `scripts/check.sh`.
- **Operator-as-scribe bottleneck.** Mitigated by one-line records and by the adjudicator doing the heavy reading.
- **Prompt-only feature under-tested.** Mitigated by the validator unit tests and the apply-models coverage of the two new roles.
